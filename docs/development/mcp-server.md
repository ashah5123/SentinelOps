# Secure MCP server and approval-gated agent operations

Phase 13 exposes a carefully scoped subset of SentinelOps through the
[Model Context Protocol](https://modelcontextprotocol.io) so compatible AI clients (Claude Code,
Codex, or any MCP-speaking agent) can investigate incidents, retrieve runbooks, and *propose*
operational actions — but never execute a state change without a human's explicit, server-verified
approval.

## SDK choice

The official Java MCP SDK: `io.modelcontextprotocol.sdk:mcp`, pinned to **`0.18.4`** (see
`services/incident-service/pom.xml`). Deliberately not the newer `2.x` line: at the time this was
built, `2.x` had diverged the Spring integration modules (`mcp-spring-webmvc`/`webflux`) out of
lockstep with `mcp-core`'s own versioning, so `0.18.4` is the last release confirmed to have both
in sync. In practice this service doesn't even depend on `mcp-spring-webmvc` — it registers the
SDK's plain-servlet transport (`HttpServletStreamableServerTransportProvider`, part of `mcp-core`)
directly as a Spring Boot `ServletRegistrationBean`, so the single `mcp` artifact (which
transitively pulls `mcp-core` + `mcp-json-jackson2`) is sufficient.

## Trust model

| Boundary | Trust level |
| --- | --- |
| MCP client (any AI tool) | Untrusted — authenticates like any other API caller, gets nothing beyond its role |
| Human operator | Trusted, but every approval is still re-verified server-side (permission, expiry, content hash, incident version) |
| MCP server (this code) | Trusted enforcement point — the only place scope/role checks happen |
| SentinelOps backend (existing services) | Trusted — MCP never bypasses it |
| Identity provider (Keycloak) | Trusted issuer of signed tokens |
| AI model output | **Untrusted** — a tool call being "confidently generated" by a model proves nothing; every argument is validated as if hostile |
| Incident/alert/runbook content | **Untrusted data** — never treated as instructions (see prompt catalog and adversarial tests) |
| External connectors (Alertmanager, generic webhook) | Out of scope for MCP directly — their own Phase 12 trust boundary is unchanged |

**Core rule:** a tool call being confidently generated by a model is never treated as authorization
to act. Every operation is bound to (1) the authenticated caller, (2) an authorized scope, (3) a
validated target resource, (4) validated parameters, (5) current domain state, and (6) — for any
mutation — a real, server-verified human approval.

- **Who may connect:** anyone holding a valid Keycloak-issued access token for this realm/audience
  (network transport), or anyone who can supply `MCP_STDIO_ACCESS_TOKEN` (stdio transport — see
  below). There is no anonymous/unauthenticated path.
- **Identity establishment:** the exact same JWT validation the REST API uses
  (`SecurityConfig`'s `JwtDecoder` — signature, issuer, audience, `exp`/`nbf`), reused by
  `McpTokenValidator`. A token minted for a different audience/service is rejected identically to
  how the REST API would reject it.
- **Roles → scopes:** SentinelOps' identity provider does not yet issue a dedicated OAuth `scope`
  claim (see `infrastructure/docker/keycloak/realm-export.json`), so MCP scopes are derived from
  the existing role model (`RoleScopeMapper`) — this phase's own instruction is to "use the
  repository's actual role model as the final authority." If a token *does* carry an explicit
  `scope` claim, it can only **narrow** access (an intersection), never widen it beyond what the
  role already implies.
- **Read-only operations:** every tool except `propose_action` (see Tool catalog).
- **Human-approval-required operations:** everything reachable through a proposal
  (acknowledge, assign, change severity, add note, escalate, resolve, replay a dead letter).
- **Never exposed:** raw request logs, complete environment configuration, access tokens/secrets,
  internal stack traces, unrestricted alert payloads (only a fingerprint prefix and metadata),
  HMAC values, or any data a role couldn't already see through the REST API.
- **Credential protection:** tokens are never logged, never placed in a tool result, never stored
  server-side beyond the single validation call. `McpToolDispatcher`/`McpResourceDispatcher` audit
  the *outcome* of a call, never its arguments verbatim.
- **Revocation:** identical to the REST API's existing behavior — a short-lived access token
  simply stops working at `exp`; there is no session or credential caching beyond one token's
  lifetime (HTTP: revalidated every request; stdio: validated once at process start, so a
  long-running stdio session is only as fresh as when it was launched — documented as a known
  limitation below).

## Transports

### Streamable HTTP (network)

Disabled by default (`sentinelops.mcp.network-transport-enabled=false` /
`MCP_NETWORK_TRANSPORT_ENABLED`). When enabled, registered at `sentinelops.mcp.endpoint-path`
(default `/mcp`) as a plain servlet (`HttpServletStreamableServerTransportProvider`), scoped to its
own Spring Security filter chain (`McpHttpTransportConfig.mcpHttpFilterChain`, ordered *before* the
main JWT-based `apiFilterChain` so it isn't swallowed by it — the same pattern Phase 12's
alert-webhook filter chain uses). That chain `permitAll()`s at the Spring Security layer
deliberately: authentication happens inside `mcpContextExtractor`, which reads the
`Authorization: Bearer` header and validates it via `McpTokenValidator` — a request with a missing
or invalid token simply gets no `McpActor` bound to its session, and every tool/resource call then
fails closed with "Authentication required." This never weakens the interactive JWT chain used
everywhere else; it is a *different*, equally real, enforcement mechanism scoped to exactly this
one path.

### stdio (local development)

`com.sentinelops.incident.mcp.transport.McpStdioLauncher` — a separate process/main-class, never
started implicitly. Since stdio has no per-request header, it requires exactly one pre-obtained
access token via the `MCP_STDIO_ACCESS_TOKEN` environment variable, validated once at startup
through the same `McpTokenValidator`. **This is the documented safe local-development
authentication method** — stdio never silently grants administrator (or any) access to "whichever
process happens to be talking to it"; a missing/invalid token refuses to start.

```bash
export MCP_STDIO_ACCESS_TOKEN="$(curl -s -X POST \
  http://localhost:8180/realms/sentinelops/protocol/openid-connect/token \
  -d grant_type=password -d client_id=sentinelops-console \
  -d username=responder-demo -d password=<password> | jq -r .access_token)"
# The repackaged Spring Boot jar needs PropertiesLauncher + -Dloader.main to run a class other
# than the application's own main() — a plain "java -cp app.jar <class>" will not work here,
# since application classes live under BOOT-INF/classes/, not the jar root.
java -Dloader.main=com.sentinelops.incident.mcp.transport.McpStdioLauncher \
  -cp services/incident-service/target/incident-service.jar \
  org.springframework.boot.loader.launch.PropertiesLauncher
```

### What's supported either way

Explicit protocol-version negotiation, graceful init/shutdown, and cancellation are handled by the
SDK itself. Bounded timeouts/response sizes/pagination are enforced by this service's own code
(`McpProperties`, `McpToolCatalog`'s truncation helpers) — see Rate limits below. Health/readiness
for network mode reuses the existing `/actuator/health` endpoint (no dedicated MCP health probe
was added — a known limitation, see below).

## Prompt catalog

`investigate_incident`, `summarize_incident`, `prepare_handoff`, `compare_related_incidents`,
`review_runbook_evidence` — see `McpPromptCatalog`. Every prompt's instructions: treat retrieved
content as untrusted data (never instructions), require citations, state when evidence is
insufficient, never ask for hidden chain-of-thought, and explicitly remind the model that it has no
ability to change incident state directly — only to propose. A prompt call is scope-gated exactly
like a tool/resource; it grants no additional authorization.

## Proposal and approval lifecycle (section 8)

**Stage 1 — Proposal** (`AgentProposalService.propose`, via the `propose_action` MCP tool *or* the
console's `POST /api/v1/incidents/{id}/proposals`): validates action-specific parameters (e.g. a
real severity value, an eligible dead-letter topic), computes a SHA-256 `content_hash` over
`(incidentId, actionType, canonicalParameters, expectedVersion)`, classifies risk
(LOW/MEDIUM/HIGH), and durably inserts a `PENDING` row in `incidents.agent_proposals` — idempotent
on a caller-supplied `idempotencyKey` (a retried request returns the existing proposal, never a
duplicate). **Nothing executes at this stage.**

**Stage 2 — Approval + execution** (`AgentApprovalService.approveAndExecute`, via
`POST /api/v1/proposals/{id}/approve`): in one transaction —

1. Reject if the approver is the same actor who proposed it (`SELF_APPROVAL`).
2. Reject a `REPLAY_DEAD_LETTER` proposal approval from a non-admin (`INSUFFICIENT_PERMISSION`).
3. Reject if the proposal isn't `PENDING` (`NOT_PENDING`) or has expired (`EXPIRED`, and the row is
   marked `EXPIRED` in the same call).
4. Mark it `APPROVED`, recording the approver, timestamp, and optional review note.
5. **Atomically consume the approval** (`UPDATE ... WHERE approval_consumed = false`) — a second,
   concurrent, or replayed call always finds the flag already set and is rejected
   (`APPROVAL_ALREADY_CONSUMED` / re-observed as `NOT_PENDING` on a full replay of the whole call).
6. **Re-verify the content hash** against what's stored — if parameters were somehow altered
   between proposal and execution, refuse (`CONTENT_HASH_MISMATCH`).
7. **Re-verify the incident's current JPA `@Version`** matches `expectedVersion` — if the incident
   changed since the proposal was reviewed, refuse (`STALE_STATE`) rather than execute against
   stale assumptions.
8. Only then call the real, existing `IncidentCommandService` method (or `DeadLetterReplayService`
   for a replay, or enqueue a notification for an escalation) — never a direct repository write.
9. Record `AGENT_PROPOSAL_EXECUTED` (or `_EXECUTION_FAILED`) in the audit trail.

Rejection (`AgentApprovalService.reject`) is a separate, simpler path: `PENDING → REJECTED`, no
execution, still audited. `ProposalExpirationScheduler` periodically marks stale `PENDING` rows
`EXPIRED` so the console reflects it without waiting for a manual approve/reject attempt.

## Authorization matrix

| Role | Read tools/resources | `propose_action` | Approve/reject (non-replay) | Approve a `REPLAY_DEAD_LETTER` proposal |
| --- | --- | --- | --- | --- |
| VIEWER | ✅ | ❌ | ❌ | ❌ |
| RESPONDER | ✅ | ✅ | ✅ (never their own proposal) | ❌ |
| ADMIN | ✅ (+ `admin:read` tools) | ✅ | ✅ | ✅ |

## Rate limits and resource controls

- `McpRateLimiter`: per-actor fixed-window request rate (`sentinelops.mcp.rate-limit`, default
  60/min) and a bounded per-actor concurrency semaphore (default 4 concurrent tool calls) —
  released in a `finally` block so a cancelled/failed call never leaks a slot.
- `ProposalRateLimiter`: per-actor proposal-creation rate (`sentinelops.proposals`, default
  10/10 min), applied in `AgentProposalService` regardless of whether the request came from MCP or
  the console's own REST endpoint.
- Page size, search-result count, and response text length are all bounded server-side
  (`McpProperties.maxPageSize`/`maxSearchResults`, and `McpToolCatalog`'s field-truncation
  helpers) — a caller cannot request an unbounded result set.

## Audit and observability

Every MCP-specific action is audited via the existing `AuditRecorder` (sanitized: tool/resource
name, outcome, correlation ID — never a raw argument, token, or full prompt):
`MCP_AUTHENTICATION_FAILED`, `MCP_AUTHORIZATION_DENIED`, `MCP_TOOL_INVOKED`,
`MCP_RESOURCE_READ`, `MCP_RATE_LIMIT_REJECTED`, `AGENT_PROPOSAL_CREATED`,
`AGENT_PROPOSAL_APPROVED`, `AGENT_PROPOSAL_REJECTED`, `AGENT_PROPOSAL_EXPIRED`,
`AGENT_PROPOSAL_EXECUTED`, `AGENT_PROPOSAL_EXECUTION_FAILED`. A denied or failed call is still
audited even though nothing executes.

`McpMetrics` (Micrometer, prefix `sentinelops.mcp.*`): active sessions, tool calls by
bounded tool name and outcome, resource reads by bounded resource type and outcome,
authentication/authorization failures, tool latency, cancellations, rate-limit rejections,
proposal outcomes, execution attempts, invalid-argument counts, and prompt-injection test-failure
counts. No incident ID, proposal ID, user ID, token, query, or error message is ever used as a
label.

## Known limitations

- No dedicated MCP health/readiness endpoint — network mode relies on the existing
  `/actuator/health`.
- The runbook resource template reuses the search index rather than a dedicated by-slug
  repository lookup, since none exists yet.
- A stdio session's identity is validated once at process start; a very long-running stdio session
  keeps using that identity until the process is restarted, even if the underlying token would
  since have expired for a fresh HTTP call. Documented, not silently hidden.
- The full agent-task evaluation suite, adversarial prompt-injection test corpus, and a Playwright
  approval-flow end-to-end test were not built in the time available for this phase — the unit
  tests in `com.sentinelops.incident.mcp.**`/`com.sentinelops.incident.proposal.**` cover the
  safety-critical server-side logic (self-approval, replay, stale-state, content-hash, admin-only
  dead-letter approval) directly, but a live-client-driven evaluation harness remains future work.
- `docker`/Testcontainers-backed verification (a live MCP client against a running Compose stack)
  could not be executed in the environment this phase was built in (`docker: command not found`)
  — see the final verification report for exactly what was and wasn't run.

## How to disable MCP network access

Set `sentinelops.mcp.network-transport-enabled=false` (the default) or leave
`MCP_NETWORK_TRANSPORT_ENABLED` unset. `McpHttpTransportConfig` is annotated
`@ConditionalOnProperty` on exactly this flag, so no servlet, no filter chain, and no
`McpSyncServer` bean for the HTTP transport are created at all — not merely a filter that rejects
requests. The stdio transport is a separate process that must be launched explicitly and is
unaffected by this flag.
